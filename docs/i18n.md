# Languages (internationalisation)

The skeleton is complete in **Catalan** (default), **Spanish** (fallback) and **English** (last
resort; the language of the code, comments, documentation and language-file keys). Specification:
"Technical baseline" › "Languages"; built in session 31.

## The language service and the fallback chain

`service('language')` is `Modules\Core\I18n\Language` (overridden in `app/Config/Services.php`).
Every `lang()` call of the modules, the themes, kpcrudy and kpapy goes through it. A line missing
in the requested locale is looked up in:

1. the requested locale (`ca-ES`);
2. the locale without its region (`ca`);
3. `Config\App::$localeFallbacks` in order (`['es', 'en']`);
4. `en` (always last).

CodeIgniter's own class only falls back to English. A key found nowhere is shown as the key.
`Language::chain()` returns the chain and `Language::has($key, $locale)` says whether a locale
defines a line itself (used by the key checks).

Content (pages, news, events, menus, projects) is not a language line: its languages are the
site's locales and its translations fall back to the site's default language (see "Content
languages" below).

## Locales of the site

`Modules\Core\I18n\Locales`:

| | Where | Default |
|---|---|---|
| Supported | `Config\App::$supportedLocales` | `ca`, `es`, `en` |
| Available | setting `Core.locales` (Settings › General, checkboxes, type `multiselect`, choices = the supported locales; at least one; rule `supported_locales`) | every supported locale |
| Default | setting `Core.defaultLocale` (Settings › General) | empty = `Config\App::$defaultLocale` (`ca`); always one of the available locales, else the first available |

`Locales::available()`, `default()`, `isAvailable()`, `name($locale)` (the language's own name,
`Core.locales.<code>`) and `names()`. Before installation (no `.env` nor lock file) only the
configuration is read.

## Negotiation

`Modules\Core\I18n\LocaleNegotiator::negotiate($profileLocale, $acceptLanguage)`: the user's
profile language, then the browser's `Accept-Language` (by quality, `es-ES` matches `es`, `*` and invalid tags
ignored), then the site's default — always among the **available** locales. Public pages take the
language of their URL instead (below).

### Language in the URL (public site)

Public pages carry their language in the URL (D-37-02, `Modules\Core\I18n\LocaleUrls`,
service `localeurls`, configuration `app/Config/LocaleUrls.php`):

- a path **without a prefix** is in the site's **default language** (`/qui-som`, `/news`), whatever
  the browser or the user's profile says;
- the other available languages carry their code as the first segment: `/es/quienes-somos`,
  `/en/news/…`, `/es/` (home page);
- `/ca/…` (the default language), a language the site does not offer and a prefix in front of a
  non-public path (`/es/backend`) redirect (301) to the path without it;
- non-public paths never carry a prefix: `Config\LocaleUrls::$excluded` (back office, `api`,
  sign-in pages, `files`, `install`, `progress`, `ical`, `sitemap.xml`, PWA, assets…); they keep
  negotiating (profile, browser, default).

How it works: `Modules\Core\I18n\LocaleRouter` (the `router` service, `app/Config/Services.php`)
reads the prefix before routing, so module routes never mention the language; the `locale` filter
applies the language it fixed (and `authsession` does not replace it with the profile's on public
pages); the application's `site_url()` (`app/Helpers/url_helper.php`, loaded before
CodeIgniter's) adds the current prefix to public paths, so every internal link of a Spanish page
stays in Spanish (`site_url('news')` → `/es/news`). `LocaleUrls::url($path, $locale)` builds the
URL of a path in a given language.

- **Language switch:** the default theme's public header shows a globe with the current code next
  to the light/dark switch (partial `partials/language_switch`, theme option `languageSwitch`,
  hidden with a single language): links to the **same page** in every available language.
- **Per-language slugs:** a module whose pages have one slug per language gives them with
  `service('localeurls')->setAlternates([locale => path])` (Pages does it); the switch and the
  `hreflang` links then use them, and Pages redirects a slug of another language to the page's path
  in the URL's language (`/es/qui-som` → `/es/quienes-somos`).
- **SEO:** the public `<head>` lists `<link rel="alternate" hreflang="…">` for every language the
  page exists in, plus `x-default` (the default language), except on `noindex` pages; the canonical
  URL is the page in the current language; the sitemap lists every page once per translation.
- Pages reserve the language codes as top-level slugs.
- `Config\LocaleUrls::$enabled = false` turns it off: public pages negotiate like the rest and the
  switch is hidden.
- A theme of its own can include the partial (`theme_partial('language_switch')`) or build its
  links from `service('localeurls')->links()`.

- Global filter `locale` (`Modules\Core\Filters\Locale`, before `csrf` and `authsession`, every
  path except `api/*` and `progress/*`): sets the request's and the language service's locale for
  everybody (guests, the login, the web installer).
- `authsession` then applies the logged-in user's profile language when the site offers it.
- `apilocale` (Api module, `api/*`): the same negotiation without a profile.
- The profile form only offers the available locales (`in_list` of them).
- Emails and notifications are rendered in the recipient's language
  (`RecipientLocale::for()`: profile language if available, else the site's default); email
  views set `<html lang>` from the language service.
- `Config\App::$negotiateLocale` stays off (the Core negotiates).

## Language files

- `Language/<locale>/<Name>.php` in every module and theme, with **exactly the same keys** in
  `ca`, `es` and `en` and no empty text.
- CodeIgniter's system texts: Spanish from `codeigniter4/translations`; Catalan copies of the
  files users see in `app/Language/ca/` (`Validation`, `Pager`, `Errors`, `Security`, `Number`,
  `Time`); the other system files (developer messages) follow the chain (Catalan → Spanish).
- Shield's texts (`Auth.*`): Spanish from Shield; Catalan in `app/Language/ca/Auth.php` for the
  keys the Auth module does not define itself.
- kpcrudy and kpapy ship `ca`, `es` and `en`.
- Translated settings (one text per site language): type `translated` (`docs/settings.md`).

## Checks

`tests/unit/I18n/LanguageKeysTest.php` (runs in CI with the rest of the suite):

- same keys in ca/es/en for every module and theme file, no file without its English one, no
  empty text;
- the Catalan copies of the system and Shield files have their keys;
- every literal key used in the code (`lang('Module.key')`) and every key of the manifests
  (resources, permissions, menus, settings, calendars) exists in the three languages;
- widgets, notifications and scheduled tasks have a title in the three languages.

`modules/Core/Tests/I18nTest.php`: the chain, the negotiation, the settings, guests, the profile
and the API.

The tests run with `app.defaultLocale=en` (`phpunit.xml.dist`) because they assert English
texts; the I18n tests set the locales they check.

## Content languages

Translated content (News posts and categories, Pages, Events and their categories, Menus labels
and custom links, Tasks projects, and any module built the same way) takes its languages from the
site's locales, never from a list in the module (session 37, D-37-01).
`Modules\Core\Content\ContentTranslations`:

| Method | What |
|---|---|
| `locales()` | available locale => its name (`Locales::names()`), in order: the tabs of a form |
| `codes()` | the available locale codes (`Locales::available()`): kpapy's `setTranslations()` |
| `defaultLocale()` | the required language and first fallback (`Locales::default()`) |
| `defaultName()` | its name in its own language, for messages and help texts ("leave it blank to build it from the title in {0}") |
| `crudOptions([...])` | kpcrudy `setTranslations()` options plus `required` = [default] and `fallbacks` = `['*' => [default]]` |
| `apiOptions([...])` | kpapy `setTranslations()` options plus `required` = [default] |
| `defaultText($texts, $field)` | the source text of a record (slugs, activity summaries, notification titles): the default language's, else the first filled-in available one |
| `texts()` / `pick()` | readers: the requested language, else the default one, else the first available one; an empty optional field also falls back to the default language |
| `keepUnavailable($edited, $stored)` | keeps the stored texts of languages no longer offered when a form saves (labels stored outside kpcrudy) |

```php
$crud->setTranslations('task_project_translations', 'project_id', 'locale', ['name', 'description'],
    ContentTranslations::locales(), ContentTranslations::crudOptions(['types' => [...], 'rules' => [...]]));
$api->setTranslations('task_project_translations', 'project_id', 'locale', ['name', 'description'],
    ContentTranslations::codes(), ContentTranslations::apiOptions());
```

kpapy's own chain (requested → `Config\Kpapy::$localeFallbacks` → `Config\App::$defaultLocale` →
the others) starts with the site's default language: `app/Config/Kpapy.php` sets
`localeFallbacks = [Locales::default()]`. Calendar events built from a language line use
`CalendarEvent::translated($key, $args)` (one text per site language) and fall back to the
default language.

Behaviour when the languages change (no migration is needed: one translation row per locale):

- **A language added** (to `Config\App::$supportedLocales` and `Core.locales`): every form shows
  an empty tab for it; readers and the API fall back to the default language until it is filled.
- **A language removed** from `Core.locales`: its rows are kept but neither shown (readers skip
  them, the API does not offer it) nor edited (no tab); saving a record keeps them (kpcrudy only
  writes the languages it shows; Pages revisions and Menus labels keep them too). Putting the
  language back shows them again.
- **The default language changed** (`Core.defaultLocale`): existing records stay readable (the
  fallback reads the new default, then any available language); the new default becomes required
  the next time a record is edited.

`tests/unit/I18n/ContentLanguagesTest.php` fails when module or theme code names a language
literally (`'ca'`, `"es"`…) outside language files, `Database/`, `Config/`, tests and the
`Locales`/`Language` classes. Module tests can configure a fourth language and another default
with `Modules\Core\Tests\ContentLocalesTrait` (`useContentLocales('fr', 'es')`,
`assertTranslationTabs($html, $field)`). Because the tests run with `app.defaultLocale=en`
(English texts), the content modules' test cases call `useShippedContentLocales()`: Catalan is
the site's default (and the required content language) and the test browser asks for English.

**Upgrading a module written for 1.0.0:** the constants `ContentTranslations::LOCALES`,
`ContentTranslations::FALLBACK_LOCALE`, `NewsRepository::FALLBACK_LOCALE`,
`News\Controllers\Posts::LOCALES` and `TranslatedText::FALLBACK_LOCALE` were removed. Replace
`ContentTranslations::LOCALES` with `ContentTranslations::locales()` (or `codes()` for kpapy), the
`FALLBACK_LOCALE` constants with `ContentTranslations::defaultLocale()`, the options
`['required' => ['ca'], 'fallbacks' => ['*' => ['ca']]]` with `ContentTranslations::crudOptions()`
(`apiOptions()` for kpapy) and `postedTranslations()['ca'][<field>]` with
`ContentTranslations::defaultText($crud->postedTranslations(), <field>)`.

## Adding a language

1. Add the code to `Config\App::$supportedLocales`. The settings `Core.defaultLocale` and
   `Core.locales` offer every supported locale (`Modules\Core\I18n\DefaultLocaleOptions`,
   `LocaleOptions`; nothing to change in the Core's manifest).
2. Add `Language/<code>/` files to every module and theme (same keys) and `Core.locales.<code>`
   (the language's own name, shown on the content tabs).
3. Add Catalan-style copies of the system files if `codeigniter4/translations` has none.
4. Extend `LanguageKeysTest::LOCALES`.
5. Tick it in Settings › General › Languages. Content needs nothing else: every translated form,
   reader and API offers it at once (empty tabs, the default language as the fallback; "Content
   languages" above). FullCalendar uses its locale file when one is vendored in
   `public/assets/vendor/fullcalendar/locales/`.
